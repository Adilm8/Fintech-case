# Интеграция BCC Business Shield в BCC Business

Документ описывает, где проверка встаёт в платёжный процесс банка, какие данные использует, как деградирует и как выводится в промышленную эксплуатацию. Пометки: **[демо]** — есть в текущей демо-версии и проверено по коду; **[цель]** — целевая архитектура, в демо не реализована.

## 1. Где стоит проверка

Проверка выполняется после того, как бухгалтер заполнил платёж (или импортировал пакет из 1С), и **до** подписания ЭЦП через NCALayer. Подпись ставится уже под проверенным платежом.

```
 Бухгалтер                 BCC Business (BFF)              Shield                 Данные
 ─────────                 ──────────────────              ──────                 ──────
 платёж / импорт 1С ─────▶ валидация формы
                           POST /api/payments/check ─────▶ предпроверка
                                                           (БИН/ИИК/БИК)   ◀──── история платежей клиента
                                                           правила риска   ◀──── реестр счетов BCC (внутренний)
                                                           скоринг         ◀──── справочник банков НБ РК
                           ◀──── вердикт + причины ─────── (≈ 3 мс)
                           │
          ┌────────────────┼──────────────────────┬───────────────────┐
        green             yellow                 red                 invalid
          │                 │                     │                   │
          ▼                 ▼                     ▼                   ▼
   NCALayer: подпись   согласование          «Отложить и          исправить
                       директора             проверить»;          реквизиты
                       (комментарий)         одобрить красный
                          │                  только директор
                          ▼                  с комментарием
                    NCALayer: подпись              │
                                                   └─▶ журнал + антифрод-аналитик

 В демо-интерфейсе «Подписать» заблокирована, пока нет допустимого вердикта
 или решения директора (см. ниже).
```

В демо-версии вместо NCALayer стоит кнопка «Подписать», которая только показывает уведомление: реальной ЭЦП и интеграции с NCALayer нет **[демо]**. Правила блокировки подписи реализованы в интерфейсе демо (на сервере подписи нет): зелёный — можно подписать; жёлтый и серый — только после согласования директором либо после отметки бухгалтера «перезвонил поставщику по номеру из договора»; красный — только после одобрения директором; платёж на согласовании или отклонённый директором, а также `invalid` — подписать нельзя **[демо]**. Каждый проверенный платёж открывается по собственному адресу `/check/{id}`.

### Сценарии входа

| Сценарий | Как работает | Статус |
|---|---|---|
| Одиночный платёж | BFF вызывает `POST /api/payments/check` на каждом платеже перед подписью | [демо] |
| Очередь на подпись | `GET /api/payments/queue`: вердикты по всем платежам очереди | [демо] |
| Пакет из 1С | Импорт пакета → пакетная проверка → зелёные платежи идут в групповую подпись, жёлтые/красные/ошибочные отцепляются на согласование, чтобы один подозрительный платёж не блокировал зарплату и налоги | [цель] |

Для пакета нужен отдельный эндпоинт (например, `POST /api/payments/check-batch`) и парсер формата выгрузки 1С; в демо их нет. Ядро проверяет платежи независимо друг от друга, поэтому пакетный режим — цикл по платежам плюс разбиение результата на группы.

## 2. Источники данных

| Источник | Что даёт | Где находится | Статус |
|---|---|---|---|
| История платежей клиента | кому, на какие реквизиты и какие суммы платил этот клиент за 12 месяцев | внутри BCC Business | [демо]: синтетика одного клиента (150 платежей, 12 поставщиков) |
| Реестр счетов BCC | владелец счёта в BCC (БИН), дата открытия | внутри BCC, наружу не выдаётся | [демо]: синтетический справочник |
| Справочник банков НБ РК | код банка, БИК, название; проверка соответствия кода в ИИК и БИК; признак бюджетных получателей (Казначейство `KKMFKZ2A`, ГК «Правительство для граждан» `GCVPKZ2A`) | публичный | [демо]: файл `data/banks.json` |
| Краткая память проверок | недавние проверки и платежи: повтор номера счёта, дробление платежей, накопленная сумма новому получателю | внутри сервиса проверки | [демо]: в памяти процесса; в продукции — БД |
| Реестр БИН/ИИН | название компании по БИН, возраст компании | в продукции — реестр юрлиц | [демо]: синтетический файл; подключение реального реестра — [цель] |

Внешних сетевых вызовов при проверке нет: все данные берутся из хранилища банка или локального справочника.

### Банковская тайна

Принцип: данные о чужом счёте используются **внутри банка**, а клиенту возвращается только факт несовпадения.

- Клиенту (бухгалтеру, директору) **[демо]**: «Счёт в BCC оформлен не на указанного получателя». Без названия владельца, без его БИН, без даты открытия счёта; сигнал «счёт открыт недавно» не раскрывает дату. Это относится ко всем ответам клиентских эндпоинтов (проверка, очередь, согласования, метрики, журнал).
- Антифрод-аналитику BCC **[демо]**: с заголовком `X-Role: analyst` ответ дополняется блоком `analyst_details` — владелец счёта (название, БИН), дата открытия и возраст счёта, точные позиции подозрительных символов в названии. В интерфейсе это переключатель «Вид аналитика антифрода» на экране директора.
- В демо заголовок `X-Role` **не аутентифицируется**: его может передать любой клиент API. В продукции роль берётся только из JWT BCC Business (раздел 9) **[цель]**.

Клиентский ответ не раскрывает владельца, БИН и дату открытия чужого счёта: это противоречило бы ст. 50 Закона «О банках и банковской деятельности»; юридическую оценку формулировок всё равно должен подтвердить комплаенс BCC. Остаточные вопросы — в [LIMITATIONS.md](LIMITATIONS.md).

## 3. Контракт API (кратко)

Эндпоинты проверки, очереди и согласований принимают `?lang=ru|kk|en` (по умолчанию `ru`; любое другое значение — `422`) и необязательный заголовок `X-Role: analyst` (см. выше). Подробности — в [backend/README.md](../backend/README.md).

| Метод и путь | Назначение |
|---|---|
| `POST /api/payments/check` | проверка одного платежа |
| `GET /api/payments/queue` | платежи, ожидающие подписи, с вердиктами |
| `GET /api/history` | профиль клиента и история платежей |
| `POST /api/approvals` | отправить платёж на согласование директору (повторная отправка того же платежа не создаёт дубль) |
| `GET /api/approvals` | список согласований (фильтры `bin`, `iik`) |
| `POST /api/approvals/{id}/decision` | решение директора: `approved` / `rejected`, комментарий, `trust_account` |
| `GET /api/audit` | последние записи журнала аудита (`limit` 1–1000) |
| `GET /api/metrics` | метрики на синтетическом наборе и прогон годовой истории клиента |
| `POST /api/demo/reset` | сброс состояния демо (в продукции отсутствует) |

**Запрос** `POST /api/payments/check`:

```json
{
  "payer_id": "client-technostroy",
  "recipient_name": "ТОО «Алатау Снаб»",
  "recipient_bin": "…12 цифр…",
  "recipient_iik": "KZ…20 символов…",
  "recipient_bik": "KCJBKZKX",
  "amount_kzt": 4900000,
  "purpose": "Оплата по счёту № 318",
  "kbe": "17",
  "knp": "710"
}
```

`kbe` и `knp` (код бенефициара и код назначения платежа) необязательны. `payer_id` необязателен (в демо подставляется единственный клиент; неизвестный `payer_id` — `422`). Невидимые символы во входных данных удаляются, ИИК и БИК приводятся к верхнему регистру.

**Ответ** (`CheckResult`):

- `ruleset_version`: версия набора правил, по которой принято решение (сейчас `2026.11.26-r3`);
- `verdict`: `green` · `yellow` · `red` · `grey` (нет истории) · `invalid` (ошибка реквизитов);
- `score` 0–100, пороги: жёлтый ≥ 30, красный ≥ 65; блокирующий факт даёт красный сразу;
- `headline`, `next_action` (основное действие: `sign` / `send_to_director` / `postpone`) на языке запроса, плюс поля `*_ru` для обратной совместимости;
- `signals[]`: `rule_id`, `points`, `severity` (`block` / `primary` / `amplifier` / `info`), `reason`, `evidence` (поле, ожидалось, получено, с какой даты);
- `comparison[]`: построчная сверка «в счёте / в истории» по названию, БИН, ИИК, БИК, банку, сумме, с позициями изменённых символов;
- `history`: число платежей поставщику, дата последнего, медианная сумма;
- `trusted`, `trusted_info`: если директор ранее подтвердил этот счёт;
- `analyst_details`: только при `X-Role: analyst`.

Правила согласования **[демо]**: красный платёж можно одобрить только с комментарием не короче 10 значимых символов; ошибочный (`invalid`) одобрить нельзя; «доверять счёту» допускается только для жёлтого платежа со сменой ИИК/банка, без блокирующих фактов и с комментарием.

Для продукции в контракт добавляются: идентификатор платёжного поручения банка, идентификатор пользователя и роль (из JWT), сохранение запроса и ответа для аудита **[цель]**.

## 4. Целевое время ответа

| Показатель | Цель (SLO) | Что есть сейчас |
|---|---|---|
| Серверное время проверки одного платежа, p95 | ≤ 50 мс | ≈ 3 мс: замер на 150 платежах синтетического клиента, локально, один процесс (среднее 2,8 мс, максимум 5,4 мс) |
| Пакет из 50 платежей | ≤ 150 мс | не реализован; по скорости одного платежа (≈ 3 мс) ориентировочно ≈ 150 мс последовательно; целевой показатель потребует распараллеливания или предрасчитанных профилей поставщиков |
| Время для пользователя (BFF + сеть + проверка) | ≤ 300 мс, чтобы проверка не ощущалась перед подписью | не измерялось |

Замер в демо не учитывает чтение из боевой базы; в продукции время определяется запросами к хранилищу (раздел 9).

## 5. Деградация

| Ситуация | Поведение | Почему |
|---|---|---|
| Сервис проверки недоступен или не ответил за тайм-аут | **fail-open с предупреждением**: платёж можно подписать, в интерфейсе показан баннер «проверка не выполнена», событие пишется в журнал | недоступность проверки не должна останавливать зарплаты и налоги |
| Вердикт `red` | **fail-closed**: основное действие — «Отложить и проверить»; одобрение только директором с комментарием | это не сбой, а найденный риск; дефолт безопасный |
| Вердикт `invalid` | подпись невозможна до исправления реквизитов | такого счёта не существует |
| Нет истории (`grey`) | по умолчанию можно подписать (с отметкой бухгалтера о сверке по телефону); если сумма выше 90-го процентиля платежей клиента — основное действие «Отправить директору»; сумма больше чем в 3 раза выше этого процентиля — жёлтый, больше чем в 10 раз — красный **[демо]** | первый платёж новому поставщику нормален, но крупный стоит проверить |

Поведение при недоступности сервиса (fail-open, баннер, запись в журнал) в демо не реализовано **[цель]**. Банк может выбрать fail-closed и при недоступности проверки для крупных сумм — это решение политики риска, а не архитектуры.

## 6. Роли

| Роль | Что делает | Статус |
|---|---|---|
| Бухгалтер | видит вердикт и причины без деталей по чужим счетам, отправляет жёлтый платёж директору, откладывает красный | [демо]: без входа; [рабочий режим]: вход и роль из сессии |
| Директор | согласует жёлтые, с комментарием одобряет или отклоняет красные, может «доверять счёту» | [демо]: без входа; [рабочий режим]: вход, роль директора, порог согласования в настройках компании |
| Антифрод-аналитик BCC | видит владельца счёта в BCC, дату открытия, позиции подозрительных символов; разбирает красные срабатывания | [демо]: заголовок `X-Role: analyst` без проверки; [рабочий режим]: роль аналитика из сессии. Блокировка счетов-дропперов — [цель] |

В продукции роли берутся из JWT BCC Business (раздел 9), а не из интерфейса.

## 7. Журнал аудита

**[демо]** Дописываемый журнал `data/audit.jsonl` (в `.gitignore`), чтение — `GET /api/audit?limit=N`. Запись создаётся на каждую проверку (`POST /api/payments/check`) и на каждое решение директора. Поля: время, `check_id`, SHA-256 канонической формы запроса (без языка), `ruleset_version`, вердикт, идентификаторы сработавших правил, действие, `approval_id` при решении. Названий, БИН, ИИК, сумм и назначений в журнале нет, только хеш и идентификаторы правил, поэтому журнал не раскрывает коммерческие данные.

Чего в демо-журнале нет **[цель]**: пользователя и роли; события подписания; защиты от изменения (только дописывание на уровне кода, не криптографическая цепочка); авторизации на чтение (`GET /api/audit` открыт). Кроме журнала, в памяти процесса хранятся согласования (с комментариями бухгалтера и директора, временем решения) и доверенные счета; они сбрасываются кнопкой «Сбросить демо».

Целевой журнал: запись на каждую проверку и решение с идентификатором пользователя и роли из JWT, действием подписи, комментарием при переопределении вердикта; хранение в БД банка со сроком по внутренней политике; доступ — аналитик и комплаенс. `ruleset_version` позволяет восстановить, по каким правилам принято решение.

## 8. План пилота

**Режим «тени» на 10–20 клиентах МСБ BCC**, 2–3 месяца. Shield вызывается на каждом платеже, вердикт записывается, **но не влияет на подпись**; клиенту он не показывается или показывается без блокировок — по решению банка.

Что нужно: выгрузка истории платежей клиентов пилота за 12 месяцев, доступ к реестру счетов BCC, хук в BFF перед NCALayer, согласование комплаенса по выводу данных.

| KPI | Как считаем | Зачем |
|---|---|---|
| Срабатываний на клиента в месяц (жёлтых и красных отдельно) | вердикты / клиенты / месяцы | реальная нагрузка ложных тревог; в демо на синтетике — 2 жёлтых за 12 месяцев на 150 платежей |
| Доля переопределений директором | одобрено директором / отправлено директору | если почти всё одобряют, правила слишком шумные |
| Время до решения | от жёлтого вердикта до подписи или отклонения | цена тревоги для клиента |
| Предотвращённая сумма | сумма платежей, отклонённых или отложенных после срабатывания и позже подтверждённых как подмена | главный экономический показатель |
| Пропущенные случаи | заявления клиентов о подмене среди платежей, прошедших зелёными | реальная полнота (recall) |

Критерий перехода к боевому режиму (пороги согласуются с банком заранее): красных срабатываний на клиента не больше порога, переопределений директором меньше порога, ни одного подтверждённого пропуска на счетах внутри BCC.

## 9. Путь в продукцию

| Шаг | Зачем |
|---|---|
| PostgreSQL для согласований, доверенных счетов, краткой памяти проверок (дубли счетов, дробление платежей) и журнала | согласования, доверенные счета и память проверок сейчас в памяти процесса и теряются при перезапуске; журнал — файл |
| Предрасчитанные профили поставщиков (счета, банки, медиана и MAD суммы по БИН) | чтобы проверка не пересчитывала историю на каждом платеже |
| Реестр счетов BCC через внутренний сервис с ограничением полей | наружу уходит только «совпадает / не совпадает» |
| Авторизация: JWT BCC Business, роли бухгалтер / директор / аналитик | в демо-режиме входа нет; в рабочем режиме есть вход и роли (сессия), но не единая учётная запись BCC Business |
| Интеграция с NCALayer на стороне BFF | подпись только после допустимого вердикта |
| Мониторинг: задержка, доля тайм-аутов, распределение вердиктов | основа для fail-open и алертов |
| Правила как таблицы решений (сейчас веса и пороги — константы в коде, версия набора правил — `ruleset_version`) | банк меняет веса и пороги без программистов |

Ядро проверки не обращается к внешним сервисам. Правила, использующие краткую память (повтор счёта, дробление за 72 часа), зависят от общего состояния, поэтому при горизонтальном масштабировании память должна жить в общей БД, а не в процессе.

## 10. Дорожная карта

1. Пакетная проверка платежей из 1С и разбиение пакета на зелёные и отцепляемые.
2. Межбанковская сверка «БИН ↔ ИИК: да/нет» по модели EU Verification of Payee через Антифрод-центр НБ РК: имя владельца счёта по-прежнему не раскрывается. Требует отдельного согласования с регулятором.
3. Сигналы по банку в целом: один новый счёт получает платежи от многих компаний (выявление дроппера внутри BCC).
4. КБе и КНП: в демо они необязательные поля запроса (`kbe_mismatch`, `knp_unusual`); в продукции нужно подтвердить, что BCC Business передаёт их на этапе проверки.
5. Распознавание счёта уже есть как помощник заполнения; дальше — сверка счёта с платёжкой и пакеты из 1С.
